# Admin Center API

Status: local presentation contract, draft pending coordination with the DIT v2 lead. Optional live reads use the source-reviewed r10 shapes; actual deployed revision is unverified. These are endpoints of this scaffold, not claims about hub r10 or its ledger. The browser never calls the hub directly. Blizz authorized read-only live hub calls; trusted SSH access has been verified; authenticated reads await the existing plaintext token file location. No live hub call has been made.

All responses are JSON and `Cache-Control: no-store`. Requests to `/api/*` require `Authorization: Bearer <owner token>`; absent or incorrect tokens receive 401. The token must be provided to the process as `ADMIN_TOKEN` and is never included in responses. No mutation endpoints exist. Optional upstream reads are restricted to `/v1/control/bots`, `/v1/control/learning` with `light=true` and `tasksOnly=true`, `/v1/control/server-status`, and explicit `/v1/control/trace` queries; each game/view has independently labeled synthetic fallback. Unknown API paths return 404. No CORS access is provided.

## GET /api/trace?gameId=&correlationId=

Requires the owner token and an explicitly configured hub URL and token file. Fetches an allowlisted read-only upstream trace only on explicit request. Accepts FFXI or SWTOR and a bounded identifier. Returns envelope kind, type, occurrence time and outcome classification/disposition/finality when reported; raw envelope bodies are omitted. At r10 the hub scans a bounded recent window and returns at most 250 records, so an empty result does not prove absence or delivery. Hub access is currently unconfigured pending the token-file decision.

## GET /api/bridge-status

Requires the owner token. Returns a bounded read-only observation of the FFXI bridge unit and private fault marker via verified SSH to Banshee. The observer caches results for 15 seconds, reports unavailable or unexpected data as unknown, and never reads chat, restarts a service, modifies a marker or returns credentials. The browser refreshes while the workspace is visible. Marker absence does not establish successful delivery; service and marker states may change between observations.

## GET /api/overview?source=mock|hub

The source defaults to `mock`; `hub` explicitly requests optional allowlisted upstream reads, and unrecognized parameters return 400. Mock mode never reads the hub token file. Returns `{ "mode": "mock" | "mixed", "hubFeeds": [...], "generatedAt": <UTC ISO timestamp>, "ownerAttention": {...}, "bots": [...], "gameStatus": [...], "serviceHealth": [...], "leads": [...], "leadMonitoring": [...], "leadActivity": [...], "leadTimeline": [...], "nudgeHistory": [...], "sessionMarkers": [...], "quotaHistory": [...], "assignmentHistory": [...], "replyEvents": [...], "modelCalls": [...], "audit": [...], "ledger": [...], "learningPlan": [...], "learning": [...], "issues": [...] }`. Owner attention reads only unexpired, pending, owner-sourced coordinator approval records scoped to the two DIT projects; it cannot capture decisions tracked elsewhere. Bot and learning records may be live or synthetic per game/view, identified by `hubFeeds` and record sources. Ledger and network/bot issue examples are synthetic; lead coverage and watcher issues use coordinator data. `gameStatus` projects a stored settings snapshot with observation time and XP rate where available; server liveness and freshness are unknown, and internal paths and MOTD are omitted. The roster and service-health examples include offline projections of synthetic r10-shaped records; registration is not presence and service status is not bot health. One FFXI learning task is passed through the offline r10 projection using a synthetic task-only fixture, and its unverified status appears as a learning attention item. Leads are a narrow read-only coordinator task-board projection. Each bot has `id`, `name`, `game`, `status`, `source`, and `observedAt`; an optional synthetic `routing` example separates `purpose`, `requested`, `effective`, `version`, `source`, `observedAt`, `availability`, and `reason`. This is an illustrative local shape, not an agreed hub contract or a real configuration. `leadActivity` contains the latest tracked coordinator task status, bounded summary and timestamp, plus checkout HEAD commit time; the latter is not attributed to a lead. Summaries resembling credential material are withheld. Missing data is unknown. Lead records have `name`, `scope`, `status`, `source`, and `observedAt`. The hub lead shows the latest tracked task status and its update timestamp if available; the Admin Center lead is unknown until board data exists. A task record does not establish current activity. `leadMonitoring` provides per-lead stall and quota states and reasons; stall is the latest exact matching coordinator watcher classification with its check time when unambiguous, otherwise unknown; quota is unknown without a connected per-lead quota source. For a known lead provider, `poolCapacity` may display the coordinator’s cached shared-provider estimate when at most 180 seconds old, with its check time; it is not an individual lead quota or a guarantee of availability. The nudge history shows up to 20 scoped coordinator watcher records or heuristic stall-watch text matches per project, without message text; elapsed reply time starts at creation and is not time to resume. A separate optional `resumeSignal` reports the first observed tool request after delivery before the next matching nudge, only for the exact unique active Codex thread and sufficient bounded-rollout coverage. It is a heuristic, not proof of resumption or causality; absent, ambiguous, truncated or unsupported cases are unknown. A past watcher classification may be stale. `leadTimeline` contains up to ten recent task events and ten attributed watcher alerts per lead, plus available current watcher and tmux session-activity timestamps, and up to ten checkout HEAD ancestry commits, with source and timestamps, without task text. Checkout commits are not attributed to leads and other branches are not covered. Session activity does not establish a stall or a stopped goal. `sessionMarkers` scans at most the latest 256 KiB of the uniquely identified Admin Center Codex rollout for narrowly matched native system-event markers, returning timestamp and classification only, not text. These are historical heuristics; missing matches do not prove an active goal or available quota. The hub/behavior-platform lead is matched through one live Claude native session with exact cwd, tmux and protocol, or through a unique coordinator Codex handoff marker and matching thread metadata. Handoff binding alone does not prove a live process. Unavailable or ambiguous bindings remain unknown with a reason. Missing watcher coverage is unknown; task events are not stall classifications. No per-lead quota history is available, and the separate pool value is a snapshot. `quotaHistory` contains up to 100 cached Codex account-window observations, pseudonymous account identifier, observed timestamp and remaining percentage; it does not attribute accounts to leads or establish current quota. A background collector reads only cached state, stores no emails or credentials, excludes SBISD entries, deduplicates and retains at most 10,000 window observations in ignored local SQLite; it never refreshes accounts. `sessionActivity` is the tmux session activity timestamp for the identified hub lead session, not a measure of progress or a stall; unverified sessions remain unknown. `replyEvents` are synthetic per-bot examples of wording origin, fallback, generation status, delivery and verification; no live reply source is wired. A generated wording result alone is not delivery evidence. `assignmentHistory` is synthetic, keyed by fixture-local bot ID, with requested/effective state and recorded time; it is not real audit or routing history. `modelCalls` are synthetic examples; null cost or quality means unknown, not zero. Audit records are synthetic examples only; no admin action is recorded. Ledger records have `correlationId`, `botId` (fixture-local identity), `bot`, `request`, `result`, and `verification`; `pending` or `unknown` must not be rendered as success. `learningPlan` is a static project planning checklist, not a live finding or verified gap; it is independent of live tasks. Learning entries have `id`, `game`, `topic`, `status`, `evidence`, `datasets`, `policy`, and `source`; r10-shaped tasks can also include `phase`, `escalation`, and `retryAt`, with missing values unknown; Synthetic network/bot examples, the dated historical FFXI bridge evidence, and read-only coordinator lead and pending-decision issues have `title`, `detail`, `status`, `scope`, `source`, and optional `updatedAt`; absent update times are unknown. A hub-binding coverage issue includes a read-only `suggestedFix` when its session cannot be identified. A watcher STOPPED classification concerns a session, not a goal; goal status remains unknown without a source. A fixture issue can carry `botId` for exact matching to a bot; absent matches do not establish health. A task-derived issue can carry a `learningId` linking to the corresponding fixture-local learning item.

The mock is intentionally small; it is not a substitute for upstream schemas, pagination, complete roster coverage, audit, usage metrics or actual policy verification. Before integration, agree with the hub lead on endpoint versions, authentication, source and freshness, pagination, correlation, error behavior, authorization, audit, and command idempotency. Treat unavailable values as unknown and unavailable actions as disabled.

## Source-reviewed hub surface (r10, b089a2c)

This is a source reading guide; Blizz has authorized read-only live calls, but access and deployed revision remain unverified. `AdminCenter.cs`, `ControlCenter.cs`, `CompanionApi.cs`, `HubApi.cs`, `HubTokens.cs` and `Program.cs` in the identified baseline are authoritative for the source revision. The listed `/v1/control/*` GET routes explicitly require an Admin Bearer and return 403 on missing/invalid authorization: `overview`, `health`, `bots?gameId=`, `bot?gameId=&key=`, `providers`, `ai-spend`, `goals?gameId=`, `learning?gameId=`, `relationships?gameId=`, `server-status?gameId=`, `companion`, and `trace?gameId=&correlationId=`. A separately configured admin listener requires Admin for `/v1/*` and returns 401 before routing. The earlier handoff reported no approved admin listener or admin token; the later owner authorization permits use of the existing hub access token for read-only calls. Keep hub credentials server-side; an existing approved token file is needed and its path remains unverified.

The source's main listener leaves `/v1/health`, `/v1/games`, `/v1/status`, `/v1/jobs`, `/v1/personas` and `/v1/scorecards` open. Knowledge list and history return metadata without the document payload's adapter-private check; individual adapter-private document payload access requires Admin or a same-game Adapter. Review exact access semantics before integration; do not assume metadata is confidential.

`bots` lists persona/body records, not confirmed presence. `trace` searches envelopes by game and correlation ID (invalid or over-128-character IDs return 400; unknown games return 404); correlation alone does not prove game outcome. `learning` caps query text at 128 characters, reports a 120-item history limit, and its light/task-only options omit evidence or other panels. `overview` caches slow aggregates for 20 seconds; its source notes full-table scans and lock contention. `health` inspects services. Notably, `bot` and `goals` call `ImportProgress` even though they are GET routes; do not assume a GET is side-effect-free. Route fields, costs and behavior must be checked against the selected revision before any authorized integration. Only the allowlisted reads are wired, on explicit Admin Center refresh; health polling is not wired.

The e8c81be candidate adds interaction and knowledge-use APIs; their presence is candidate-only and does not establish live deployment. Per-bot model switching and complete spend attribution are not implemented in either handoff revision.

The proposed per-bot routing contract is in `dit-v2-release-20261027/custody/per-bot-model-routing-draft.md`. It is design only: no read or write endpoint has been agreed or implemented. Future UI must preserve verified identity and requested versus effective state, report unavailable/stale reasons, and never infer per-bot routing or attributed cost from current global provider and ledger data. Blizz approved the design draft; model controls remain disabled pending the hub implementation and separate authorization for live changes.
